============================================================
PRIMARY GOAL
============================================================

Make the postcard workflow genuinely usable offline.

The required demo flow is:

1. User is online and loads the app.
2. User goes offline / airplane mode.
3. User creates a postcard.
4. The postcard appears immediately in the UI.
5. The postcard is persisted in IndexedDB.
6. The sync operation is persisted in the IndexedDB outbox.
7. User reloads the page while still offline.
8. The postcard is still visible.
9. User reconnects.
10. The app automatically synchronizes the pending postcard using:

   POST /api/postcards

11. Retries MUST reuse the SAME postcard/client UUID.
12. The server must not receive duplicate postcards.
13. After successful sync, the local postcard is marked synced.
14. The corresponding outbox operation is cleared or marked completed according to the existing offline-db contract.
15. The final UI contains one postcard, not a duplicated local/server pair.

Core principle:

"Connectivity affects synchronization, not usability."

STEP 3 — LOCAL-FIRST POSTCARD CREATION
============================================================

When the user creates a postcard:

Generate ONE stable UUID at creation time.

That SAME UUID must be:

- the local postcard ID
- the entity_id in the outbox operation
- included in the POST /api/postcards payload
- reused on every retry

NEVER generate a new UUID during synchronization.

The postcard should be persisted locally BEFORE attempting the network request.

Expected conceptual sequence:

create postcard
→ assign stable UUID
→ save postcard to IndexedDB with pending state
→ enqueue postcard.create operation
→ update in-memory state/UI immediately
→ if online, attempt flush
→ if offline, stop there successfully

The user must not receive an error merely because there is no connection.

Offline creation is a successful local action.

============================================================
STEP 4 — PERSISTENT OUTBOX
============================================================

Implement a real persistent outbox using the existing IndexedDB store.

Use the documented lifecycle:

pending
syncing
synced
failed_permanent

For postcard.create operations:

SUCCESS / 2xx:
- mark postcard synced
- remove or complete the outbox operation according to helper design
- retain the local postcard
- later server pull must reconcile it by ID without duplication

NETWORK FAILURE:
- keep operation retryable
- return status to pending
- increment attempts if supported
- record useful last_error
- do not lose postcard

HTTP 5xx:
- retryable
- keep pending
- increment attempts
- record last_error

HTTP 4xx:
- permanent failure
- mark failed_permanent
- DO NOT automatically retry forever
- keep the postcard locally so the user does not lose their content
- expose enough state for the UI to show that synchronization failed

Do not treat every fetch error as a permanent failure.

============================================================
STEP 5 — FLUSH / SYNCHRONIZATION
============================================================

Implement a real flush() around the persistent IndexedDB outbox.

Requirements:

- read pending operations from IndexedDB
- process only supported operation types
- use the existing POST /api/postcards endpoint
- preserve payload compatibility with current Phase 2 backend
- preserve explicit client UUID
- avoid duplicate simultaneous sends
- prevent multiple flush() calls from racing
- retries must remain safe
- one failed operation must not corrupt other operations

If a flush is already in progress, a second invocation should not start an independent competing drain.

Navigator online status is a hint, not proof that the backend is reachable.

The actual fetch result determines success/failure.

============================================================
STEP 6 — BOOT / RELOAD SURVIVAL
============================================================

On application boot:

1. Open IndexedDB.
2. Load locally persisted postcards.
3. Hydrate them into the app state BEFORE depending on the network.
4. Render them so offline reload works.
5. Detect current connectivity.
6. If connectivity is available:
   - attempt pending outbox synchronization
   - then pull/reconcile server state
7. If connectivity is unavailable:
   - remain fully usable with local data

The app must not require a successful backend request to render locally saved postcards.

============================================================
STEP 7 — SERVER / LOCAL RECONCILIATION
============================================================

Update pull/reconciliation behavior so local and server postcards do not duplicate.

Use postcard ID as the primary identity.

Rules:

- same ID local + server = ONE logical postcard
- pending local postcard must remain visible
- synced server version may replace/merge the local synced representation
- server pull must not remove unsynchronized local postcards
- reconnect + pull must not produce two copies of the same postcard

Be conservative with merging.

Do not silently discard local pending content.
